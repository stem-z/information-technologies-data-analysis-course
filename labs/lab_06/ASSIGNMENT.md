# Лабораторная работа № 6

## Документирование аналитического контура

Продолжите свой проект после ЛР № 5. Используйте готовые данные, код и сохранённые результаты предыдущих работ.

1. Составьте схему происхождения данных (data lineage).
2. Проследите маршрут от выбранного значения метрики до исходного датасета.
3. Разберите, какие результаты затронет одно возможное изменение.

## Что нужно подготовить

Оформите результат лабораторной работы в файле `docs/lineage.md`. Используйте маппинг полей из `docs/mart.md`
и определения метрик из `docs/metrics.md`. При необходимости уточните их в этих же документах.

Для `docs/lineage.md` подойдёт следующая структура:

1. **Контекст анализа**  
   В подразделах "Вопрос", "Выбранное значение метрики" и "Исходные данные" опишите,
   на какой вопрос отвечает анализ, какое значение метрики выбрано и какие исходные данные использованы.
2. **Схема происхождения данных (data lineage)**  
   Покажите контур от источника до результатов ЛР № 5. Под схемой укажите, где выполняются преобразования и где
   посмотреть результаты проверок.
3. **Маршрут данных для выбранного значения метрики**  
   Начните с выбранного значения метрики и пройдите через SQL, витрину и подготовку данных до исходного датасета в
   `raw`. Добавьте подраздел "Словарь ключевых полей".
4. **Влияние одного изменения**  
   Назовите раздел по выбранному сценарию, например "Влияние изменения справочника зон". Объясните, какие данные и
   метрики затронет изменение.

## Порядок работы

### 1. Выберите значение метрики и укажите исходные данные

Возьмите один вопрос из ЛР № 5 и одно значение метрики. Укажите единицу измерения, период и срез. Для среднего или доли
укажите, сколько записей или значений вошло в расчёт.

Укажите первоисточник, способ загрузки и путь к исходному датасету в `raw`.

### 2. Составьте схему происхождения данных

Покажите фактический путь от источника через `raw`, `staging` и `mart` до результатов ЛР № 5. Включите общий
итог, основную и уточняющую группировки и выборку отдельных числовых значений. Используйте имена из своего проекта.
Для файлов укажите слой и имя, для таблиц - имя и место создания. Отметьте временные таблицы DuckDB, если они
используются в проекте.

Добавьте существенные входы и выходы, если они есть в вашем проекте. Например, покажите справочник как вход в
соединение, карантин как отдельный выход шага качества.

Оформите схему mermaid-диаграммой направленных связей. Для каждого перехода укажите, что происходит с данными.

Под схемой укажите файлы, в которых выполняются загрузка, подготовка данных, сборка витрины и расчёт метрик.
Кратко опишите существенные ключи соединений, фильтры, правила качества и результаты уже выполненных проверок.
Например, после соединения со справочником число строк витрины совпало с числом строк `staging`.

### 3. Проследите маршрут данных для выбранного значения метрики

Начните с сохранённого вывода. Укажите файл и ячейку, где видно выбранное значение. Если результат выведен таблицей,
укажите строку или условие отбора и столбец. Найдите SQL-запрос, который рассчитывает значение. Объясните формулу,
группировку и правила включения записей. Для доли или среднего укажите знаменатель либо число значений,
использованных в расчёте. Если результат зависит от пропусков (`NULL`), отрицательных или других значений,
поясните, как они учитываются.

Затем найдите запрос, который формирует входные данные для расчёта, и укажите, какую витрину он читает и как отбирает строки.
Выберите минимум 3 ключевых поля витрины. Для каждого объясните его роль в формуле, фильтре или группировке. Покажите,
как эти поля получены при сборке витрины из staging и какие поля исходного датасета в `raw` за ними
стоят. Если несколько полей витрины получены из одного исходного поля, укажите эту связь. Для `count(*)` объясните,
что означает одна строка, почему она входит в расчёт и откуда взялось поле группировки, если оно есть.

В таблице ключевых полей укажите смысл, тип, единицы измерения, источник, преобразование и роль в расчёте.
Укажите, где находится полный маппинг полей (из ЛР № 4). Для остальных метрик достаточно определений из `docs/metrics.md`.

### 4. Разберите одно возможное изменение

Выберите одно возможное изменение, например изменение поля справочника, ключа,
типа или формулы метрики. По схеме и коду определите, на каком шаге возникнет изменение, какие наборы данных и метрики
оно затронет и через какое поле, join, фильтр или правило группировки. Укажите, повлияет ли оно на выбранное
значение метрики.

### 5. Проверьте документ и подготовьте Pull Request

- [ ] В контексте анализа указаны вопрос, значение метрики, первоисточник и точный путь
  к данным в `raw`.
- [ ] Схема ведёт от источника к результатам ЛР № 5.
- [ ] Выбранное значение метрики можно найти в результатах ЛР 5. Из маршрута и словаря понятно, как оно рассчитывается
  и откуда берутся ключевые поля.
- [ ] Объяснено, какие данные и метрики затронет выбранное изменение и повлияет ли оно на выбранное значение.

Сдайте Pull Request из `lab-06` в `main` своего репозитория.
