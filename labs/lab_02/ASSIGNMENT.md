# Лабораторная работа № 2

## Ingestion и слой raw в локальном Data Lake

### Цель работы

Реализуйте воспроизводимую загрузку исходных файлов своего проекта в неизменяемый слой `raw` локального объектного
хранилища MinIO. Оркестрацию загрузки выполните в Apache Airflow, а доступность загруженного файла проверьте через
DuckDB.

Работа продолжает контур курса:

```text
Источник → raw → staging → mart → анализ и отчёт.
```

В этой работе реализуется только перенос исходных данных в `raw`.

### Результат работы

В репозитории настроена локально запускаемая инфраструктура и DAG `ingest_raw`, который:

- Ожидает доступность основного HTTP-источника (Wait).
- Скачивает исходный файл по HTTP без изменения байтов (Pull).
- Загружает неизменённые файлы в бакет `raw` MinIO, создавая партицию по логической дате Airflow.
- Не создаёт дубликаты и не изменяет существующий raw-объект при повторном запуске с той же датой.

DuckDB читает загруженный файл непосредственно из MinIO. Это подтверждает, что данные доступны аналитическому
инструменту без переноса в транзакционную базу данных.

Используйте источник, который был принят в вашем `Project Brief` ЛР № 1. Условия для источника:

### Шаг 3. Запустите инфраструктуру

Каркас проекта уже содержит `docker-compose.yml`, `pyproject.toml`, `uv.lock` и `.env.example`.

1. Создайте `.env` по образцу `.env.example` и не добавляйте его в Git.
2. Задайте в `.env` подключения Airflow через переменные `AIRFLOW_CONN_*`:
    - `minio_s3_conn` типа Amazon Web Services с учётными данными MinIO и `endpoint_url: http://minio:9000`.
    - `source_http_conn` типа HTTP с базовым URL вашего источника.
3. Установите Python-зависимости командой `uv sync --locked`.
4. Поднимите сервисы командой `docker compose up --build -d`.

Должны работать MinIO, служебная БД Airflow и сам Airflow. MinIO API доступен на порту `9000`, а Console - на порту
`9001`.
airflow: http://localhost:8080/
minio: http://localhost:9001/

### Шаг 4. Проверьте инфраструктуру

После старта убедитесь, что:

1. Открывается MinIO Console.
2. Открывается Airflow.

Бакет `raw` появляется при первой успешной загрузки сырых данных в MinIO. До этого его отсутствие в MinIO Console нормально.

### Шаг 5. Реализуйте сенсор (Wait)

В DAG `ingest_raw` создайте задачу `wait_for_primary_source` на базе `HttpSensor`. Она должна проверять доступность
основного файла вашего источника:

- Connection: `source_http_conn`.
- Метод: `HEAD` или `GET`.
- `poke_interval`: `60` секунд.
- `timeout`: `600` секунд.

После таймаута сенсора загрузка в `raw` не выполняется. Автоматического fallback нет: сенсор остаётся фактической
зависимостью процесса.

После сохранения файла DAG убедитесь, что Airflow видит `ingest_raw`.

### Шаг 6. Реализуйте загрузку (Pull)

Добавьте задачу `load_to_raw` на `PythonOperator`, которая выполняется после успешного срабатывания сенсора.

1. Получает из DAG через `op_kwargs` URL, имя файла, `dataset_slug` и идентификатор S3 Connection.
2. Формирует ключ объекта по шаблону:

   ```text
   s3://raw/<dataset_slug>/ingested_on={{ ds }}/<имя_файла>
   ```

3. Проверяет через S3 API, существует ли объект по этому ключу.
4. Если объект уже существует, завершает задачу успешно без загрузки и без изменения объекта.
5. Если объекта нет, получает байты HTTP-файла и загружает их в MinIO через `S3Hook.load_bytes`.

`{{ ds }}` - логическая дата Airflow, передаваемая через `kwargs`, а не текущая физическая дата. Она описывает запуск
ingestion, а не дату события в данных.

Сохранённый raw-объект должен быть идентичен HTTP-ответу. Не преобразовывайте, не распаковывайте, не очищайте и не
меняйте формат данных до загрузки.

### Ручной fallback на GitHub

Этот сценарий не требуется для успешного обычного запуска. Он применяется только если первоисточник недоступен, а
нужно воспроизвести загрузку из зафиксированного снимка.

1. Убедитесь, что файл из `data/source/` закоммичен и доступен в GitHub.
2. Замените `SOURCE_URL` в `airflow/dags/ingest_raw.py` на GitHub raw URL этого файла, закреплённый за конкретным
   commit SHA.
3. Замените host в `AIRFLOW_CONN_SOURCE_HTTP_CONN` в `.env` на `https://raw.githubusercontent.com`.
4. Выполните `docker compose up -d --force-recreate airflow-webserver airflow-scheduler`.
5. Запустите тот же DAG повторно.

Такой fallback выполняется тем же кодом и через тот же HTTP-путь. Он не требует ветвления DAG или отдельной задачи.

### Шаг 7. Проверьте результат через DuckDB

Используйте `scripts/read_raw.py` из каркаса или напишите небольшой Python-скрипт либо Jupyter-ноутбук, который
подключается к локальному MinIO и выводит первые строки загруженного файла средствами DuckDB.

Настройте S3 endpoint для MinIO и выберите функцию чтения по формату файла: `read_csv_auto` для CSV,
`read_json_auto` для JSON, JSONL и NDJSON или `read_parquet` для Parquet. Файл читается по пути вида:

```text
s3://raw/<dataset_slug>/ingested_on=<логическая_дата>/<имя_файла>
```

Для скрипта из каркаса передайте этот путь явно:

```bash
uv run --env-file .env python scripts/read_raw.py --path \
  "s3://raw/<dataset_slug>/ingested_on=<логическая_дата>/<имя_файла>"
```

Проверка DuckDB не должна создавать таблицы, новые файлы или staging-преобразования.

## Useful commands

Все команды выполняйте из корня репозитория проекта, например `itad-labs`.

Запустить лабораторный стенд:

```bash
docker compose up --build -d
```

Посмотреть логи сервисов:

```bash
docker compose logs -f
```

Остановить лабораторный стенд, сохранив данные:

```bash
docker compose down
```

Полностью сбросить лабораторный стенд:

```bash
docker compose down -v
```

`docker compose down -v` удаляет Docker volumes, т.е. будут удалены:
- загруженные raw-файлы в MinIO
- метаданные Airflow (включая историю запусков DAG)
