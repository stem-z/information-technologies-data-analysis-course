# Лабораторная работа № 4

## Проектирование и сборка аналитической витрины

### Цель работы

Продолжите сквозной проект после ЛР № 3. Возьмите подготовленный `staging.parquet`, спроектируйте небольшую аналитическую витрину и сохраните её в слое `mart` в локальном S3-хранилище стенда. Витрина должна поддерживать выбранный вопрос из принятого `Project Brief` и сохранять понятный смысл одной строки.

Выберите **один вопрос** из принятого `Project Brief`: основной или любой уточняющий. Для выполнения лабораторной достаточно подготовить витрину для этого вопроса. Состав полей, меры, срезы и проверки определяйте относительно выбранного вопроса.

Контур курса:

```text
Источник → raw → staging → mart → SQL-метрики → анализ и отчёт.
```

В этой работе выполняется участок `staging → mart`. Основная логика реализуется явными SQL-запросами в Jupyter-ноутбуке. 
Витрина должна содержать данные, необходимые для ответа на выбранный вопрос. Для каждой таблицы витрины должно быть чётко определено, что собой представляет одна строка.

### Результат работы

Подготовьте jupyter-ноутбук, краткое описание модели и сохранённую витрину.
Витрина может состоять из одной широкой таблицы или основной таблицы и отдельных таблиц измерений. Описательные атрибуты измерений можно хранить непосредственно в широкой таблице. Выберите структуру, которую считаете обоснованной для своего вопроса и данных, и кратко объясните решение.
ER-диаграмма не является обязательной.

Ориентировочное время самостоятельной работы - **90 минут** при готовом стенде, выполненной ЛР № 3 и использовании демонстрационного репозитория. Демонстрация преподавателя проходит отдельно и в это время не входит.

## 2. Обязательные артефакты

Подготовьте два файла:

```text
notebooks/build_mart.ipynb
docs/mart.md
```

В `docs/mart.md` достаточно трёх коротких разделов:

1. **Модель.** Выбранный вопрос, гранулярность, ключ либо ограничение его определения, меры и правила будущей агрегации, обоснование выбранной структуры.
2. **Сопоставление полей.** Таблица происхождения всех выходных полей.
3. **Проверки и ограничения.** Ссылка на раздел проверок ноутбука, краткий итог и ограничения.

Не копируйте SQL и все результаты из ноутбука в документ.

Сохраните как минимум один Parquet-объект основной таблицы:

```text
s3://mart/<dataset_slug>/source_ingested_on=<логическая_дата>/<mart_name>.parquet
```

Имя `<mart_name>` должно отражать смысл таблицы, например `trips`, `hourly_rentals`,  `listings` и т.п. Логическая дата совпадает со значением в пути входного `staging`, а не с текущей датой выполнения.

Если вы выделяете измерение в самостоятельную таблицу, сохраните её отдельным Parquet-объектом в том же выходном префиксе. Например:

```text
s3://mart/<dataset_slug>/source_ingested_on=<логическая_дата>/dim_<dimension_name>.parquet
```

Атрибуты измерений, включённые в широкую таблицу, сохраняются вместе с ней и не требуют отдельных объектов.

### Шаг 2. Определите гранулярность, ключ и меры

До написания преобразования закончите предложение:

> Одна строка таблицы `<mart_name>` представляет …

Возможные примеры:

- Одну сохранённую запись о поездке из выбранного снимка.
- Один час наблюдения системы велопроката в определённую дату.
- Один день наблюдения.
- Одно объявление о жилье в выбранном снимке.
- Одну страну в одном календарном году.

Если исходные данные уже агрегированы по часу или дню, сохраните этот уровень детализации. `COUNT(*)` в таком наборе считает строки наблюдений, а число событий может храниться в отдельной мере. Не объединяйте в одной таблице часовые и дневные итоги как одинаковые наблюдения.

Опишите идентификацию строки одним из двух способов:

- Если есть обоснованный естественный или составной ключ, укажите его поля и смысл. В проверках подтвердите отсутствие пропусков и недопустимых повторов.
- Если надёжного бизнес-ключа нет, явно укажите это ограничение. Само отсутствие ключа не является основанием для удаления строк и не позволяет утверждать доказанную уникальность реальных событий.

Технический номер строки или хеш сам по себе не доказывает уникальность события. Создавать такой идентификатор для выполнения формального требования не нужно. Не применяйте `DISTINCT` для получения искусственной уникальности: разные исходные строки могут совпасть по выбранным аналитическим полям. Сошлитесь на решение о повторах из ЛР № 3.

Для каждой меры укажите единицу измерения, её использование в выбранном вопросе (расчёт показателя или сравнение значений) и допустимость суммирования по времени и другим срезам. Например, число аренд за непересекающиеся часы можно суммировать, средние значения нельзя складывать или усреднять без учёта весов, а цену объявления в снимке нельзя трактовать как выручку. Не восстанавливайте отдельные события из готовых агрегатов.

Для временных полей различайте время события или период наблюдения, дату сбора исходного снимка и логическую дату загрузки. Если источник содержит только снимок объектов, это не история изменений. Дата загрузки не заменяет отсутствующее время события или сбора снимка.

Если для выбранного вопроса необходима дополнительная фильтрация данных, явно укажите условие, причину и фактическое число исключённых строк. Сверьте баланс входных, сохранённых и исключённых строк `count(входных строк) = count(сохранённых строк) + count(исключённых строк)`.
Такая фильтрация не должна подменять решения качества из ЛР № 3 (см. пример ниже). Также не допускается скрытая фильтрация.

Например:
> В ЛР3 отрицательная сумма оплаты признана допустимой для сохранения в `staging` с соответствующим флагом. Такие записи сохранены, поскольку они остаются полезными для подсчёта поездок, хотя их сумма может исключаться из расчёта средней стоимости.
>
> Если в ЛР4 удалить все такие записи как "некорректные", изменится и количество поездок. Это фактически новое решение о качестве.

Для записи итоговой витрины на S3 можно воспользоваться способом из ЛР № 3. Повторное выполнение должно перезаписывать файлы предыдущего выполнения.

Если в модели используются `JOIN`, до записи результата проверьте уникальность ключей справочников, ожидаемую кардинальность, число строк до и после каждого соединения и число ненайденных соответствий. `LEFT JOIN` сохраняет строки без соответствия, но не защищает от размножения при повторяющихся ключах справа. Объясните все изменения числа строк, если они обоснованы.

### Шаг 5. Проверьте записанный результат

Прочитайте из S3-бакета `mart` сохранённый объект. Выполните проверки на прочитанном файле. В ноутбуке сохраните конкретные запросы, видимые результаты и короткие пояснения.

1. **Количество и схема.**
	- Сравните числа строк во входном `staging` и в сохранённом датамарте. При обоснованном изменении количества строк объясните его.

2. **Ключ и обязательные поля.**
	- Если ключ существует, отдельно проверьте пропуски и повторы.
	- Проверьте наличие полей, без которых теряется заявленный смысл строки.

3. **Меры и вычисленные поля.** 
	- Проверьте отсутствие пропусков (`NULL`) в мерах, которые по вашей модели должны быть заполнены в каждой строке. Если пропуски допустимы, сравните их количество со `staging` с учётом выполненных преобразований и объясните появление новых пропусков, если оно обосновано.
	- Проверьте, что минимальные и максимальные значения мер не противоречат смыслу полей и принятым правилам ЛР № 3.
	- Для вычисленных полей проверьте диапазон или набор значений, который следует из их определения. Например, час начала события должен быть от 0 до 23, а ISO-номер дня недели - от 1 до 7.

4. **Флаги и преобразования.** 
	- Для строк, включённых в витрину, проверьте, что значения, помеченные флагами качества в ЛР № 3, перенесены в витрину вместе с соответствующими флагами. Например, отрицательная сумма, оставленная с флагом, должна сохранить своё значение, а не заменяться нулём или `NULL`.

5. **Пригодность для выбранного вопроса.**
	- Выполните один короткий запрос по срезу, нужному для выбранного вопроса, например группировку с подсчётом строк. Объясните, что именно он подтверждает.
	- Полный набор метрик, сравнения и содержательные выводы здесь не нужны.

Если созданы отдельные таблицы измерений, прочитайте также каждую из них, проверьте уникальность ключа и количество ссылок из основной таблицы без соответствия в измерении. Для всех джойнов сохраните результаты проверок кардинальности и количества строк.

Пример проверки пропусков и повторов существующего ключа:

```sql
SELECT count(*) AS null_keys
FROM read_parquet('s3://mart/<...>/<mart_name>.parquet')
WHERE row_key IS NULL;

SELECT row_key, count(*) AS rows_per_key
FROM read_parquet('s3://mart/<...>/<mart_name>.parquet')
WHERE row_key IS NOT NULL
GROUP BY row_key
HAVING count(*) > 1;
```

Для составного ключа проверьте `NULL` в каждом компоненте и используйте все поля в `GROUP BY`. Приведённый пример не требует создавать отсутствующий ключ.
