# Лабораторная работа № 3

## Профилирование и качество данных: переход от raw к staging

### Цель работы

Освоить методы профилирования, проверки качества и воспроизводимой подготовки данных для дальнейшего анализа.

Контур курса:

```text
Источник → raw → staging → mart → анализ и отчёт.
```

В этой работе реализуется только участок `raw → staging`.  
Витрина, расчёт бизнес-метрик, преобразования при помощи `dbt`
и автоматизация с использованием `airflow` в эту работу не входят.

### Результат работы

В репозитории проекта есть исполняемый Jupyter-ноутбук и краткий отчёт, которые для датасета из raw-слоя:

- Читают данные непосредственно из S3 с помощью DuckDB.
- Описывают фактическую схему, гранулярность и свойства набора.
- Выполняют не менее пяти явно заданных правил качества.
- Создают Parquet-файл в слое нормализованных данных (`staging`) и карантин (также в виде Parquet-файла).
- Фиксируют результаты проверок, решения и ограничения в отчёте.

Исходный датасет в `raw` при этом не изменяется, не перезаписывается и не удаляется.

Работа ведётся в отдельной ветке `lab-03`, созданной на основе версии проекта с выполненной ЛР № 2. Для сдачи работы

Для профилирования используется датасет из слоя `raw`. Его полный S3-путь указывается в отчёте

## 2. Термины и границы

- `raw` - слой исходных данных. Файлы сохраняются в том виде, в котором получены из источника, без изменения
  содержимого и формата. Это позволяет повторять обработку с другими правилами и проверять результат по исходным данным.

- `staging` - слой нормализованных данных. В нём согласованы имена и типы полей, приведены к единому виду форматы
  значений, добавлены признаки нарушений качества и оставлены записи, допустимые для дальнейшей обработки.

- **Карантин** - отдельный набор записей, исключённых из дальнейшей обработки из-за критических нарушений качества. Для
  каждой записи сохраняются причина исключения и исходные данные, необходимые для разбора проблемы.

- **Правило качества** - короткое проверяемое условие для поля, ключа или связи полей, связанное с аналитической задачей
  проекта. Для правила задаются строки, к которым оно применяется, допустимое число или доля нарушений, критичность
  нарушения и действие по проблемным записям: оставить, пометить, преобразовать или перенести в карантин.

Не нужно:

- Проектировать витрину или рассчитывать итоговые бизнес-показатели.
- Переносить преобразования в `dbt`.
- Добавлять новый DAG Airflow или менять логику ingestion.
- Изменять объект из бакета `raw` или заменять его "очищенным" файлом.

## 4. Маршрут выполнения

### Шаг 0. Обновите каркас и перейдите с MinIO на SeaweedFS

Если выполнение ЛР № 2 начиналось уже на новом каркасе (с SeaweedFS), данный шаг пропускайте и переходите к Шагу 1.

В актуальном каркасе лабораторных работ MinIO заменён на SeaweedFS. Слои `raw`, `staging` и `mart` и формат S3-путей
сохраняются, но меняются сервис хранилища, порты и параметры подключения. Выполните этот шаг в своём проектном
репозитории до написания кода ЛР № 3.

1. Убедитесь, что выбрана ваша рабочая ветка `lab-03` и нет незакоммиченных изменений.

   ```bash
   git branch --show-current
   git status
   ```

   Если рабочее дерево содержит изменения, сохраните свою работу отдельным коммитом перед слиянием. Не добавляйте
   `.env` в Git. Ветка должна содержать реализацию ЛР № 2, включая DAG, исходный датасет и `Project Brief`.

2. Подключите репозиторий преподавателя как `upstream`. `origin` должен по-прежнему указывать на репозиторий вашей
   команды. Проверьте текущие адреса:

   ```bash
   git remote -v
   ```

   Если `upstream` ещё не добавлен, выполните:

   ```bash
   git remote add upstream https://github.com/stem-z/itad-labs.git
   ```

   Если `upstream` уже существует, убедитесь, что он указывает на этот каркас (`itad-labs.git`). Повторно добавлять его
   не нужно.

3. Получите изменения и влейте `main` каркаса в текущую ветку:

   ```bash
   git fetch upstream
   git merge --no-edit upstream/main
   ```

   Команда `merge` выполняется в вашей ветке `lab-03`. Она добавляет обновления каркаса к вашей реализации.

   Если возникают конфликты, разрешите их и завершите слияние.

4. Обновите локальный `.env` по новому `.env.example`. Merge меняет образец, но не ваш `.env`, поскольку этот файл
   не хранится в Git. Замените параметры подключения к хранилищу:

   | Было в версии с MinIO | Должно быть в версии с SeaweedFS |
   | --- | --- |
   | `MINIO_ROOT_USER` | `S3_ACCESS_KEY` |
   | `MINIO_ROOT_PASSWORD` | `S3_SECRET_KEY` |
   | `MINIO_S3_ENDPOINT=localhost:9000` | `S3_ENDPOINT=localhost:8333` |
   | `AIRFLOW_CONN_MINIO_S3_CONN` | `AIRFLOW_CONN_S3_CONN` |
   | Connection ID `minio_s3_conn` | Connection ID `s3_conn` |
   | Endpoint в Airflow `http://minio:9000` | Endpoint в Airflow `http://seaweedfs:8333` |

   Пример согласованных настроек локального стенда из каркаса:

   ```dotenv
   S3_ACCESS_KEY=s3admin
   S3_SECRET_KEY=s3admin123
   S3_ENDPOINT=localhost:8333
   AIRFLOW_CONN_S3_CONN={"conn_type":"aws","login":"s3admin","password":"s3admin123","extra":{"endpoint_url":"http://seaweedfs:8333","region_name":"us-east-1"}}
   ```

   При своих ключах укажите те же значения в `login` и `password` подключения Airflow. Сохраните параметры
   PostgreSQL, учётной записи Airflow, `AIRFLOW_FERNET_KEY` и `AIRFLOW_CONN_SOURCE_HTTP_CONN` из своего `.env`.
   Не заменяйте файл целиком образцом: адрес HTTP-источника должен остаться адресом вашего датасета.

5. Согласуйте с новым подключением код своей ЛР № 2. В DAG замените идентификатор `minio_s3_conn` на `s3_conn`
   там, где он передаётся в `S3Hook` или функцию загрузки. В собственном скрипте чтения raw замените имена
   переменных `MINIO_*` на соответствующие `S3_*` из таблицы выше и старый endpoint - на `localhost:8333`.
   Для DuckDB сохраните `s3_url_style = 'path'` и `s3_use_ssl = false`. При запуске кода внутри контейнера
   используется `seaweedfs:8333`; при запуске через `uv` на компьютере - `localhost:8333`.

   Если в проекте есть локальный `dbt/profiles.yml`, согласуйте параметры доступа к S3 с обновлённым
   `dbt/profiles.yml.example`. Запускать модели `dbt` для этой работы не требуется.

6. Запустите обновлённый стенд:

   ```bash
   uv sync --locked
   docker compose up --build -d
   docker compose ps
   ```

   Дождитесь статуса `healthy`, откройте Airflow по адресу `http://localhost:8080/`
   и файловый интерфейс SeaweedFS по адресу `http://localhost:8888/buckets/`.
   В хранилище должны быть бакеты `raw`, `staging` и `mart`. Если сервис не готов, посмотрите его логи:

   ```bash
   docker compose logs seaweedfs airflow-scheduler airflow-webserver
   ```

7. Загрузите исходный датасет в S3 через DAG, подготовленный в ЛР № 2. Дождитесь успешного выполнения ingestion и
   используйте полученный полный S3-путь как вход ЛР № 3. Значение `ingested_on` соответствует логической дате
   этого запуска Airflow.

   Убедитесь, что DuckDB читает загруженный объект, используя `scripts/read_raw.py` или свой скрипт из ЛР № 2:

   ```bash
   uv run --env-file .env python scripts/read_raw.py --path \
     "s3://raw/<dataset_slug>/ingested_on=<логическая_дата>/<имя_файла>"
   ```

8. Привязка к удалённому репозиторию upstream больше не нужна. Её можно удалить:
   ```bash
   git remote remove upstream
   ```

9. На этом этапе можно закоммитить изменения, чтобы отделить инфраструктурное выравнивание
   от непосредственно кода лабораторной работы.
   ```bash
   git commit -am "lab-03: Align S3 settings with SeaweedFS"
   ```

Обновление каркаса и технические изменения подключения входят в Pull Request ЛР № 3. Продолжайте профилирование
после успешного чтения датасета из S3.

### Шаг 3. Сформулируйте и реализуйте правила качества

Выберите не менее пяти правил для полей из профиля. Начните с гипотез о качестве из `Project Brief`,
уточнив их по фактическим данным. Каждое правило оформите отдельным блоком ноутбука:
описание в Markdown-ячейке, конкретный запрос и расчёт результата в кодовой ячейке, затем видимый вывод проверки.

Для каждого правила укажите:

- Идентификатор (`id`) - стабильное уникальное имя правила.
- Поле, составной ключ или связь полей, к которым относится правило.
- Проверяемые строки: например, все записи или только завершённые заказы.
- Проверяемое условие.
- Порог - допустимое число или долю нарушений; укажите единицу измерения и предельное значение.
- Критичность: `critical`, `warning` или `info`.
- Действие по нарушившим записям: `quarantine`, `flag` или `report_only`.
- Связь с задачей: метрику, фильтр или срез из `Project Brief` и последствия нарушения для анализа.

Если порог задаётся числом записей, он должен быть неотрицательным целым числом; если долей - числом от 0 до 1.
Для базовой работы достаточно одной выбранной единицы порога. Можно задать для всех правил допустимое число
нарушений, равное нулю, если любое нарушение требует внимания. Порог задавайте переменной в ячейке ноутбука
и используйте при сравнении, а не только упоминайте в описании. Превышение фиксируется, когда число или доля
нарушений больше заданного порога.

Порог оценивает результат проверки набора данных. Действие применяется к каждой проблемной записи
независимо от того, превышен ли общий порог.

Значения действий означают:

- `quarantine` - исключить запись из `staging` и сохранить в карантине. В этой работе применяется к критическим нарушениям.
- `flag` - оставить запись в `staging` и добавить явный признак нарушения.
- `report_only` - сохранить запись без изменения по этому правилу и отразить результат проверки в сводке и отчёте.

Однозначные преобразования имён, типов и форматов описываются отдельно как часть нормализации в шаге 4.

Пример описания правила для задачи сравнения неотрицательных цен:

> Правило `non_negative_price`. Проверяем поле `price` среди строк с заполненной ценой.
> Допустимое значение - неотрицательное; порог - ноль нарушений. Критичность - `critical`,
> действие - `quarantine`: отрицательная цена искажает среднюю и медианную цену по районам.

Поле, проверяемые строки, условие, порог и действие должны быть обоснованы для вашего источника и задачи.

Не менее пяти правил должны совместно охватывать следующие свойства данных:

1. Уникальность записей с учётом гранулярности и бизнес-ключа, если ключ существует.
2. Полноту значимого для вопроса поля.
3. Допустимость значения: тип, формат, диапазон или справочник категорий.
4. Согласованность связанных полей, например порядок дат, соответствие статуса и суммы или вложенных полей JSON.

Для каждого правила объясните связь с метрикой, фильтром или срезом из `Project Brief`.

Для каждого правила получите и включите в одну таблицу отчёта:

- Число проверенных строк.
- Число и долю нарушений.
- Допустимый порог и результат сравнения с ним.
- Действие по записям, нарушившим правило.

В ноутбуке покажите итоговую сводную таблицу по всем правилам.

### Шаг 4. Подготовьте нормализованные данные и карантин

На основе выполненных проверок подготовьте два результата и запишите их в бакет `staging` на S3.
Для этого достаточно SQL-запросов с явными преобразованиями, условиями отбора и признаками нарушений.
Бакет создаётся автоматически при запуске стенда. Создавать его в коде ЛР № 3 не требуется.

Используйте следующие пути вывода:

```text
s3://staging/<dataset_slug>/source_ingested_on=<логическая_дата>/staging.parquet
s3://staging/<dataset_slug>/source_ingested_on=<логическая_дата>/quarantine.parquet
```

Здесь `<логическая_дата>` совпадает с `ingested_on` у исходного raw-объекта, а не с текущей датой запуска.

Требования к `staging.parquet`:

- Имена и типы выбранных аналитических полей пригодны для дальнейшего анализа. Если исходные имена и типы уже
  подходят, искусственно менять их не нужно. Необходимые переименования и приведения типов выполняются явно.
- В нём нет строк, нарушивших `critical`-правило с действием `quarantine`.
- Записи с действием `flag` имеют явный признак нарушения. Имя признака и смысл его значений описаны в отчёте.
- В нём нет бизнес-агрегаций, итоговых метрик и "исправлений по догадке".

Требования к `quarantine.parquet`:

- Файл создаётся при каждом запуске, включая запуск без исключённых записей. Пустой файл имеет определённую схему.
- Сохранены исходные поля исключённых записей.
- Поле `quality_rule_ids` содержит идентификаторы правил, по которым запись исключена, а `quarantine_reason` -
  понятное объяснение причины исключения. Формат перечисления нескольких идентификаторов описан в отчёте.
- Каждая исключённая запись попадает в карантин один раз. При нескольких критических нарушениях сохраняются все
  причины исключения.

Не восстанавливайте неизвестные значения по догадке. Преобразования, например приведение строки к дате, должны
быть однозначными. В отчёте достаточно коротко перечислить фактически изменённые поля и добавленные признаки.

Если запись нарушила несколько правил, карантин имеет приоритет перед сохранением с флагом: запись исключается
один раз, все причины исключения сохраняются. Если критических нарушений нет, карантин остаётся пустым;
специально создавать ошибки в исходных данных не нужно.

Исходный объект в `raw` сохраняется без изменений. Повторное выполнение с тем же raw-путём, параметрами и правилами
должен давать те же количества строк в `staging` и карантине и не добавлять дубликаты.

## 5. Требования к ноутбуку

Основной исполняемый артефакт - `notebooks/profile_quality.ipynb`.
В нём последовательно читаются данные, рассчитывается профиль, выполняются пять конкретных проверок,
подготавливаются два результата и записываются в S3.

Рекомендуемая структура:

1. Контекст, параметры и подключение к S3.
2. Профиль: схема, пропуски, повторы, период и одно распределение.
3. Правила: отдельные пары Markdown-ячеек и ячеек с кодом, затем сводная таблица.
4. Подготовка staging и карантина, примеры записей и запись файлов.
5. Короткие пояснения для отдельного отчёта.
6. Чтение сохранённых результатов и проверки качества.

Не переносите весь код в одну длинную ячейку. SQL-проверки должны быть видны рядом с описаниями правил,
а не скрыты за вызовом одного большого внешнего модуля.

Входной S3-путь, аналитический период и выходной префикс задаются в ячейке параметров.
Если нужен справочник, явно укажите его S3-путь там же. Пороги правил задаются переменными в соответствующих ячейках.
